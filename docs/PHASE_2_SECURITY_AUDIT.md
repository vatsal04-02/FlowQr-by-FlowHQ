# Phase 2 security audit (2026-11-15)

**What this is.** A structured internal review of FlowQR's own code, configuration and deployment, done by reading the code in each area, attacking it with tests that run against the real application and a real PostgreSQL 16, and probing a staging stack over HTTPS. It extends `docs/SECURITY_AUDIT.md` (2026-11-14, upload / AI / tenant targets).

**What this is not.** It is **not** an independent penetration test, a code audit by a third party, or a certification. It does not cover Google's, Razorpay's, Cashfree's or the AI provider's systems, the host operating system or cloud account of a real server (none exists yet), or load and denial-of-service resilience. Reading and testing 271 routes found the issues below; an attacker with more time may find others. Treat "no further findings" as "none found by this method", never as "secure".

**Method.** (1) Every route was enumerated with the access dependency it declares (`docs/evidence/phase2/route-access-matrix.txt`) and then pinned by a test, so a new or loosened route fails the suite until a person reviews it. (2) Role sweeps call every route as a lower role than it needs. (3) The database was interrogated for row-level security on every tenant table and for what the application role is allowed to do. (4) Authentication, session, OAuth, token, rate-limit, logging, background-job and autonomy code was read line by line (files listed in section 3). (5) A staging stack (production overlay, `APP_ENV=staging`, strict config guard, HTTPS through Caddy) was attacked with spoofed headers and scanned for leaked values in logs.

## 1. Findings

| # | Severity | Finding | Status |
|---|---|---|---|
| **F1** | **High** (before launch) | **Administrator takeover by sign-up.** Registering with an address that is in `PLATFORM_ADMIN_EMAILS` made the new account a platform administrator **immediately, without proving the mailbox**. Anyone who registered that address before its owner did would have had full access to every business, billing and the admin tools. The Google sign-in path already required a verified address; the password sign-up path did not | **Fixed.** Sign-up never grants admin. The flag is granted when the address is verified (`auth.platform_admin_granted` is audited), and `require_platform_admin` independently refuses an unverified address (defence in depth). `python -m app.cli set-admin-password` also verifies the address (whoever can run it on the server controls the account) and grants the flag. 4 regression tests, each shown to fail on the old code |
| **F2** | Medium | Platform-admin sign-ins lasted 14 days, like any customer's | **Fixed.** Admin sessions last at most `ADMIN_SESSION_TTL_HOURS` (12); sessions opened before the grant are shortened too. Tested |
| **F3** | **Blocker** (functional, found only on staging) | **The marketing site could not work behind Caddy.** The marketing host proxied only `/`, `/pricing` and assets; every other marketing page (`/about`, `/demo`, `/review-cards`, the legal pages...), `robots.txt`, `sitemap.xml` and the images were redirected to the app domain, **and the three public API calls the marketing pages make were redirected too, so the pricing page showed "Talk to us for pricing" instead of the plans**. Nothing on a developer laptop shows this, because everything is one origin there | **Fixed.** The marketing host serves every marketing path and exactly three public API paths (`GET /billing/plans`, `GET /legal/info`, `POST /public/leads`, body limited to 64 KB); every other API path on that host still redirects. `deploy/staging/check_routes.sh` now checks all of it (40 checks) |
| **F4** | Low | The web server's access log recorded the full request URL including the query string, so the Google OAuth `code` and `state` of every connection would be stored in the logs | **Fixed.** `code`, `state`, `token`, `access_token`, `id_token`, `refresh_token`, `key`, `api_key` values are replaced by `[redacted]` in the access log. Tested |
| **F5** | Low | `NEXT_PUBLIC_SITE_URL` was never passed to the frontend build, so canonical links, social cards and `sitemap.xml` would have pointed at `http://localhost:3000` in production. `robots.txt` disallowed `/ai`, which by prefix also blocked the marketing page `/ai-growth-agent` | **Fixed.** Build argument added (`.env.example`, compose, Dockerfile, `docs/ENVIRONMENT_VARIABLES.md`); the robots rule is now `/ai/` and `/ai$`. Verified on staging (sitemap and canonical link carry the staging origin) |
| F6 | Info | Login lockout is per email (10 failures in 15 minutes) in addition to per address, so someone who knows an email can lock that account out for up to 15 minutes. This includes the admin address | **Accepted.** The alternative (lock per address only) lets a distributed guesser try forever. Argon2id and the 10-character mixed-case rule make guessing impractical; a lockout is the lesser harm. Revisit if it is ever abused |
| F7 | Info | No second factor for platform administrators | **Open, owner decision.** Recommended before real customers: a hardware key or authenticator app for admin accounts. Not built in this pass. Mitigations in place: 12-hour sessions, verified address, every admin write is audited |
| F8 | Info | `POST /auth/register` answers 409 for an address that already has an account (account existence is visible) | **Accepted.** Rate-limited (10 a minute per address). Login and password reset answer identically for known and unknown addresses (tested) |
| F9 | Info | One person can create up to five businesses, each with a free trial | **Accepted for the pilot.** Cost is bounded by per-business AI and Places ceilings and by the plan allowances; watch Admin > Finance for repeat sign-ups before opening to the public |
| F10 | Info | The API is started with `--forwarded-allow-ips=*`, i.e. it believes any `X-Forwarded-For` it receives | **Safe only because the API is never reachable except through Caddy.** The production overlay removes the published port. Verified on staging: spoofed `X-Forwarded-For` and `X-Real-IP` did not evade the rate limit. **Never publish port 8000.** A host firewall that allows only 80 and 443 is the second layer |

No other confirmed vulnerability was found. Findings F1 to F5 were fixed and have regression tests; F6 to F10 are decisions or accepted risks, not fixes.

## 2. Areas covered

| Area | Result | Evidence |
|---|---|---|
| Sign-in and authentication | Argon2id; equal-time failure for unknown users; identical answers for known and unknown accounts; per-address and per-email limits; passwords 10 to 128 characters, mixed case. **Fixed F1.** No MFA (F7) | `test_login_does_not_reveal_whether_an_account_exists_and_locks_after_repeated_failures`, `test_phase2_security_audit.py` F1 tests, `test_auth_and_tenancy.py` |
| Session handling | Opaque 256-bit tokens stored only as SHA-256; `HttpOnly`, `Secure`, `SameSite=Lax`; server-side revocation; logout kills the stolen cookie; change and reset of password end other sessions; reset and verification tokens are single-use with expiry. Fixed lifetime (14 days customers, 12 hours admins), no idle timeout (accepted) | `test_expired_and_revoked_sessions_are_refused_and_logout_really_ends_the_session`, `test_password_change_and_reset_end_other_sessions_and_reset_tokens_work_once` |
| Token expiry and refresh | Google access tokens refresh 60 s before expiry; `invalid_grant` marks the connection revoked and clears the access token; a missing refresh token fails closed | `test_google_and_reviews.py` (refresh, revocation), read of `services/google/tokens.py` |
| OAuth state validation | Business connection: HMAC-signed state bound to tenant and user, plus a per-browser nonce cookie, plus a session check, plus an admin-role check at callback. Google sign-in: state, nonce and PKCE (S256) in one signed, 10-minute, path-scoped cookie; email used only when Google says verified; unverified pre-registered accounts refused. The business-connect state has no embedded timestamp (the cookie bounds it to 10 minutes; the code is single-use at Google): accepted | `test_google_sign_in.py`, `test_google_and_reviews.py` |
| Google refresh-token protection | Fernet-encrypted at rest; never returned by any endpoint or export; not in logs; export excludes secret columns by name; a restore without `TOKEN_ENCRYPTION_KEY` leaves connections unreadable (documented in `DATABASE_BACKUP_RESTORE.md`) | `test_refresh_token_encrypted_at_rest_and_never_returned`, `test_account_lifecycle.py` |
| Tenant isolation | Every tenant table has `FORCE ROW LEVEL SECURITY` and a policy (asserted over the live catalogue, 30+ tables); the application role is not superuser, not `BYPASSRLS` and owns no table; each API route also checks the tenant in code; the `X-Tenant-Id` header can only select among the caller's own memberships; a signed-in user with no business and one with another business are refused by every business route | `test_every_tenant_table_has_forced_row_level_security_and_a_policy`, `test_the_application_role_cannot_bypass_row_level_security_or_own_tables`, `test_member_routes_refuse_a_signed_in_user_with_no_business_and_a_user_of_another_business`, `test_security_audit.py`, `test_phase2_ops_and_isolation.py` |
| Role-based permissions | Three roles (owner, admin, staff) plus per-location scope for staff. Staff are refused by every admin-level and owner-level route; admins by every owner-level route; business owners by every platform-admin route (all by sweep, so new routes are covered automatically) | the three role-sweep tests |
| API authorisation | Anonymous callers refused everywhere except a reviewed list; the list of public routes that change data is pinned (login, register, password reset and verification, the payment webhook, and the two token-addressed public customer flows); the route access manifest fails on any change | `test_every_non_public_route_refuses_anonymous_requests`, `test_route_access_manifest_has_not_drifted`, `test_every_route_is_classified_and_nothing_mutating_is_public_by_accident` |
| Admin access | 56 platform-admin routes behind `require_platform_admin` (verified address required, 12-hour session, RLS bypass set only inside it); every admin write audited with the actor | role sweep; `test_admin.py` |
| Rate limiting | Redis-backed fixed windows with in-process fallback; limits on login, registration, reset, verification, public scan, miss-guessing, review generation, lead form, export, client-error relay. The limiter keys on the connecting address, which behind Caddy is the real client (verified on staging); with Redis down it falls back to per-process counters (weaker, not off) | `test_security_audit.py`, `test_public_ai.py`; staging probe |
| CSRF | Every mutating cookie-authenticated route requires the per-session `X-CSRF-Token`; `SameSite=Lax` cookies; JSON bodies only | `test_every_mutating_route_requires_the_csrf_header_for_cookie_sessions` |
| Secrets and environment variables | Strict config guard refuses development secrets, insecure cookies, localhost URLs, sink SMTP and test payment keys when `APP_ENV` is staging or production (it ran on staging); `.env*` ignored by git; CI job scans tracked files for key-shaped strings; no secret in any committed file (scan before the checkpoint commit found only test fixtures) | `test_config_guard.py`; checkpoint scan |
| Sensitive information in logs | Mailer logs no body or link in staging/production; error reporting strips bodies, cookies, headers and local variables; **F4 fixed**; staging logs after the smoke and browser runs contained no secret value | `test_access_logs_never_keep_oauth_codes_or_tokens_from_query_strings`, `docs/evidence/phase2/README.md` |
| Database access | Application role cannot update or delete `audit_logs`, `subscription_events`, `api_usage_ledger` or `ai_call_ledger` (privileges asserted); migrations run as a separate owner role; the API never holds the owner password in staging/production (separate `MIGRATION_DATABASE_URL`) | `test_append_only_ledgers_cannot_be_changed_or_deleted_by_the_application_role` |
| Background-task permissions | Workers run in a bypass session by design, so each job re-checks what a request would have checked: suspended, deleting or inactive businesses are skipped; a reply approved by a person is re-checked against that person's current membership and location scope before it is sent (`member_may_act`); feature and plan checks run again at execution | read of `workers/tasks.py`, `services/agent/executor.py`, `content_exec.py`; `test_phase2_autonomy_plan.py`, `test_phase15_governed.py` |
| Autonomy execution permissions | Policy level is computed by code, never by the model; a standing authorisation is honoured only while autonomy is on, not suspended, the plan includes `autonomy`, and the type is pre-authorised; posts, photos and replies always need a person; a business can switch everything off, and a platform administrator can stop all autonomy platform-wide; every step is in an append-only history. Phase 1.5 rules unchanged | `test_phase1_policy.py`, `test_phase1_executor.py`, `test_phase15_governed.py`, `test_autonomy.py` |
| Payment webhook | HMAC-SHA256 signature, constant-time comparison, `event_id` unique (replays do nothing), unsigned or badly signed requests get 400. **The webhook and payment code are Razorpay's; the owner has chosen Cashfree and deferred payment integration. Nothing about Cashfree was built or tested** | `test_billing.py`; staging probe (unsigned webhook gets 400) |
| Deployment surface | HTTPS with HSTS, `X-Frame-Options: DENY`, `nosniff`, referrer and permissions policies; API docs and OpenAPI hidden in staging/production; request body limits per host; database, Redis and API ports not published | `docs/evidence/phase2/staging-routes-and-tls.txt` |

## 4. Not covered (do not read this audit as covering these)

* **Independent penetration test** of a deployed server, TLS configuration, WAF, host hardening. None exists yet.
* **Dependency and supply-chain review** beyond the previous audit's `pip-audit` and `npm audit` (both clean on 2026-11-14); they were not re-run in this pass.
* **Real Google, Places, AI and payment providers.** Their behaviour was never exercised (no credentials); nothing here says anything about their security or about the keys' scopes.
* **Content security policy** `script-src` (needs per-request nonces; accepted earlier).
* **Load and abuse at scale**: fixed-window limits were tested for correctness, not under traffic.
* **Social engineering and operations**: who holds the admin and the `TOKEN_ENCRYPTION_KEY`, how the backup passphrase is kept, offboarding.
* **Two items from `SECURITY_AUDIT.md` remain the owner's**: rotate the Places key that was pasted into a chat (finding 7 there) and set a new admin password (finding 8; the command is in `docs/PRODUCTION_DEPLOYMENT.md`).
